Multi-Agent Debate System

Three copies of the same 9B model, three different reasoning procedures, one anonymized critic, deterministic vote math, and an honest dissent appendix.

The claim this project makes: orchestration alone — no bigger model, no more parameters — produces a measurable accuracy gain over a single call to the same model. Every proposer, the critic, and the aggregator all run qwen3.5:9b on the same local Ollama server; the only things that differ are system prompt and temperature.

Architecture

One debate is a fixed pipeline, run strictly sequentially against a shared local Ollama server (see framework decision for why sequential, not asyncio.gather):

Question
→
3 proposers (Analyst / Skeptic / Creative)
→
Critic scores, anonymized A/B/C
→
Rebuttal round
→
Critic re-scores
→
Deterministic vote
→
Aggregator: answer + confidence + dissent

Every arrow in that pipeline is a validated Pydantic message, not free text — Proposal, Critique, Rebuttal, FinalVerdict (see src/debate/messages.py). Every LLM call goes through a JSON-mode request plus a one-shot validate/repair retry (src/debate/structured.py): if the model's first attempt fails schema validation, the retry prompt includes the bad output and the exact field errors, which is what keeps a 9B model's shaky first-try JSON compliance from becoming free-text soup between stages. This is the same pattern project-01 (Structured Output Agent) established — a lesson pulled forward from project-05, where letting agents pass prose between stages let small errors compound silently.

Why same-model diversity is real, not cosmetic

It would be easy to fake diversity with three system prompts that just say "be an analyst" / "be a skeptic" / "be creative" and call it a day — that's a costume, and a 9B model asked to role-play a costume mostly produces the same reasoning with different adjectives sprinkled in. personas.py avoids this by giving each persona a mandatory reasoning procedure, not a personality:

Analyst (t=0.3)

Restate the question → list every given constraint → numbered steps with explicit arithmetic → answer last. Forced to do the arithmetic instead of pattern-matching to an intuitive response.

Skeptic (t=0.7)

Identify the tempting intuitive answer first → explicitly re-check it against every stated constraint → hunt for hidden assumptions or edge cases → only then commit. This is the role that catches the bat-and-ball trap.

Creative (t=1.0)

Generate at least two structurally different approaches before picking one → state why the chosen approach won → work it through. Exists because the first angle of attack isn't always the right one.

Because the procedure is mandatory (spelled out as numbered steps in the system prompt, not a vibe), the three transcripts genuinely diverge in how they got to an answer, which is exactly the raw material the critic and rebuttal round need to work with. Temperature is varied on top of this for good measure, but the procedure difference is doing most of the work — you can see this directly in a transcript: the Skeptic's reasoning field explicitly re-derives and checks the "$0.10" trap even when it ends up agreeing with the Analyst, while the Analyst's reasoning field never mentions the trap at all.

Anonymized critic + deterministic vote math

Two deliberate constraints keep the outcome auditable rather than "trust the LLM one more time":

The critic never sees persona identity

critic.py maps persona names to letters (Analyst→A, Skeptic→B, Creative→C, stable within a debate) before building the critic prompt, and the critic system prompt only ever refers to "Proposal A/B/C." This is a bias control: a critic that knows "this is the Creative persona's answer" is primed to expect — and either forgive or over-discount — unconventional reasoning. Role separation is structural, not a prompt request: critic.py has no code path that calls a proposer persona, so the critic cannot propose an answer even if a prompt-injected question tried to talk it into one.

The vote is arithmetic, not another LLM call

voting.py computes score = critic_total × agreement_multiplier where critic_total is the sum of the rubric's three 1-10 dimensions and agreement_multiplier rewards independent corroboration from other proposers (up to +20% for unanimous agreement). A "clear winner" is a top score that leads its nearest disagreeing competitor by more than 15% — tied scores between proposers who gave the same answer are treated as consensus, not a split, since a literal tie only signals disagreement when it's a tie between different answers. This whole computation is pure Python: tests/test_voting.py exhaustively covers the threshold boundary, exact ties, and the unanimous-tie edge case, with zero network calls and zero LLM non-determinism to work around.

The aggregator can't blend answers into mush

aggregator.py makes exactly one LLM call, and it produces only the reasoning_summary prose — the actual answer, confidence, is_split flag, and dissent list are all set in code from the vote's output before that call happens. The LLM cannot change which proposal won; if its summary call fails schema validation twice, the system falls back to a deterministic templated summary rather than losing an already-correct verdict to a formatting hiccup. When the vote doesn't clear the 15% threshold, the top scorer is still picked and attributed by name (never averaged with the runner-up into a hedge), is_split is set true, and every proposer whose final-round answer disagrees with the winner is grouped into a DissentEntry and appended to the verdict — dissent never silently disappears.

Framework decision: ag2 investigation → hand-rolled fallback

Decision: hand-rolled asyncio-free sequential orchestration, not ag2/AutoGen

The spec called for AutoGen (ag2) with its Ollama/OpenAI-compatible client. Verification in M1 turned up two real problems within the first ~15 minutes, well inside the authorized 30-minute budget for a fallback:

  1. The PyPI package named ag2 is not AutoGen. It resolves to an unrelated, namespace-squatted project (modules like a2a, mcp_ui, hitl — agent-protocol tooling, not a multi-agent debate framework).
  2. The actual historical package, pyautogen, now installs Microsoft's rewritten autogen-agentchat / autogen-core stack (v0.4+). That rewrite dropped the classic ConversableAgent + llm_config API the spec's language assumed, in favor of an async actor-model runtime built around ChatCompletionClient objects — a different API surface entirely, designed for open-ended conversational agent chat.

Even setting the version churn aside, this project's hardest requirements — anonymizing proposals before the critic sees them, computing the vote as deterministic arithmetic with zero LLM involvement, and assembling rebuttal-round prompts from a specific mix of the proposer's own critique plus anonymized peer critiques — are tight pipeline control flow, not conversational turn-taking. Every one of the five milestones would have meant fighting an actor-model abstraction built for a different shape of problem. The debate mechanics matter more than the framework badge, so the fallback path was taken immediately rather than spending the rest of the budget forcing a fit.

What was built instead (client.py, structured.py) is the same OpenAI-SDK-pointed-at-Ollama + Pydantic-validate-with-repair-retry pattern project-01 established for structured extraction — proven, small, and fully under this project's control. The architecture in the spec (fan-out → anonymized critique → rebuttal → re-critique → vote → aggregate, hard-capped at 2 rounds) is preserved exactly; only the plumbing underneath each call changed.

The honest cost story

A full debate makes roughly 9 sequential LLM calls per question: 3 proposals + 1 batched critique + 3 rebuttals + 1 batched re-critique + 1 aggregator summary. Self-consistency makes 3. Single-shot makes 1. That's the "≈7× tokens" the spec asks to justify — actual per-question token multiples from this machine's runs are in the bench results below.

Debate is not free lunch, and the bench is built to say exactly when it's worth the multiple rather than assert it uniformly:

  • Reasoning puzzles with a classic trap (bat-and-ball, lily pad) are where debate should earn its keep: a single Analyst call is exactly what falls into the intuitive-wrong-answer trap, and the Skeptic + critic + rebuttal loop is purpose-built to catch it.
  • Fermi estimation questions have no single correct answer, only a plausible range — self-consistency's 3-sample majority is a much cheaper way to get a stable central estimate than a full debate, and the bench should show whether debate's extra cost buys any real accuracy over that cheaper baseline.
  • Pros/cons and code-review verdicts are where a critic catching one wrong assumption (a missed cost term, a missed security issue) can flip a confident-but-wrong single-shot answer — but only if that assumption is the kind of thing the rubric's correctness_risk dimension actually surfaces.

Bench results

30 questions, stratified 8 reasoning-puzzle / 8 estimation / 7 pros-cons / 7 code-review (bench/questions.jsonl), graded automatically — numeric answers against a reference range, decision/verdict answers against an instructed short label (e.g. "Job A" vs "Job B") rather than free-text keyword matching, to keep auto-grading honest without an LLM judge. Full command: uv run python bench/run_bench.py. The committed run below is the ~6-question stratified subset (2 reasoning-puzzle, 2 estimation, 1 pros-cons, 1 code-review — bench/questions.jsonl rows with "subset": true), run with:

Install & run

# requires: Python 3.11+, uv, a local Ollama server with qwen3.5:9b pulled
git clone <this repo> && cd 09-multi-agent-debate
uv sync

# sanity check the model is reachable
curl -s http://localhost:11434/api/version

# run the fast test suite (zero network, <1s)
uv run pytest

# run the one live end-to-end test (needs Ollama, several minutes on a 9B model)
uv run pytest -m integration tests/test_integration.py -v

Model name lives in exactly one place: src/debate/config.py (override with the DEBATE_MODEL env var). Ollama base URL, timeouts, round cap, and vote thresholds live there too.

Demo walkthrough

1. The money shot: visible error correction

uv run debate ask "A bat and ball cost \$1.10 total; the bat costs \$1 more than the ball. What does the ball cost?" --live

Watch for: the Analyst proposing the intuitive-wrong $0.10 in round 1, the critic flagging low correctness_risk on that proposal, and the rebuttal round where the Analyst either revises to $0.05 or explicitly defends $0.10 against the critique. A committed sample transcript from a live run against this exact question is in transcripts/ (see debate replay below).

2. Estimation with a range and confidence

uv run debate ask "Estimate the number of piano tuners in Chicago." --live

Three genuinely different approaches (the Analyst's population/household chain, the Skeptic's check on tuning-frequency assumptions, the Creative's alternate framing) synthesized into one answer with a confidence score driven by how much the three actually agreed.

3. A genuine split

Any question close enough that the critic-weighted vote doesn't clear the 15% lead threshold — the CLI output includes is_split: true and the dissent appendix lists exactly who held out and what they proposed instead.

4. Replay a committed transcript

uv run debate replay 1

5. Bench table

uv run debate bench --subset
